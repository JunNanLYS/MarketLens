### 1. [CRITICAL] `backend/collectors/base.py:91,147` — Provider.close() 在无 mixin 子类抛 AttributeError

**实验验证**:
```
$ uv run python -c "..."
Plain.close() FAILED: 'super' object has no attribute 'close'
```

**影响范围**: 8 个 Provider 中 `WeStockProvider` / `TencentNewsProvider` 两个抛 `AttributeError`(`NeoDataProvider` 自身 override 幸免)。每次 `lifespan` 关闭时被外层 `except` 静默吞,日志报"关闭 Provider 失败"。

**修复方案** (用户确认: 方案 B - 改 pass no-op):
- `StructuredProvider.close()` 改 `return None`,更新 docstring 说明 mixin 自身是叶子节点
- `NewsProvider.close()` 同步

**验证**: 3 个新测试 + 191 个 collectors 测试全过。

**关联提交**: `fix(collectors): 修复 Provider.close() 在无 _HttpClientMixin 子类上抛 AttributeError`

### 2. [MAJOR] `backend/services/portfolio_service.py:25,96,138` — 3 个账户写端点漏 `_WRITE_LOCK`

**风险**:
- CLAUDE.md 第 209-213 行硬约束要求所有写路径持锁
- `update_account` 的 check-then-act 查重可被并发绕过
- `create_account` 漏锁导致 UNIQUE INDEX 兜底,用户看到误导性"已存在"错误
- `delete_account` 与并发 transaction 竞争同一 sqlite 连接

**修复**:
- 三个方法外层加 `with _WRITE_LOCK:`,与 `create_transaction` 范式一致
- 早返回 `return dict(existing)` 保持在锁内,确保读到一致状态

**验证**: 5 个新测试(3 个并发锁测试 + 2 个类型过滤测试),portfolio_service 测试 64/64 全过。

**关联提交**: `fix(portfolio): 补齐 create/update/delete_account 的 _WRITE_LOCK 写锁 + 类型过滤`

### 3. [MAJOR] `backend/services/evidence_builder.py:305-330` — `build_multi` 累加无截断

**实验验证**:

### 4. [MAJOR] `backend/scheduler/jobs.py:48-120,369` + `backend/main.py:69-70` — 同步 IO 阻塞 event loop

**根因**: `_check_neo_data_token_on_startup` 是同步函数,在 async lifespan 中被调用,内部 `client.get_token_status()` 走 `TokenManager._read_cache()` 同步文件读。

**修复方案** (用户确认: 方案 C - async + main.py 包裹):
- `_check_neo_data_token_on_startup` 改 `async def`,`get_token_status` 用 `await asyncio.to_thread(...)` 包裹
- `SchedulerManager.start` 改 `async def start`,内部 `_cleanup_naive_run_logs_once` 改 `await asyncio.to_thread`
- `main.py::lifespan` 改 `await _scheduler_manager.start()`
- 配套: 4 个旧测试改 `async def`(因为目标函数已 sync 变 async)

**验证**: 3 个新测试(async 函数签名 + 持锁验证),全项目 488/488 测试通过。

**关联提交**: `fix(scheduler): NeoData 健康检查改 async + main.py 启动期 to_thread 包裹`

### 5. [MAJOR] `backend/services/news_service.py:174-178,219-245` — `collect_news` 状态机误判

**问题**:
- `collected=0, skipped=0`(provider 全空)→ 误判 `success`
- `collected=0, skipped>0`(全 skip 稳态)→ 误判 `failure`
- finally 块用 `SELECT 1 WHERE started_at=?` 探测脆弱,易产生重复行

**修复方案**: 4 状态机映射 + `status="unknown"` 哨兵:

| all_items | tracked_symbols | collected | skipped | 状态 | error_message |
|-----------|-----------------|-----------|---------|------|---------------|
| 空 | 空 | 0 | 0 | success | None |
| 空 | 有 | 0 | 0 | failure | "所有 news provider 均无返回或全部失败" |
| 有 | any | > 0 | any | success | None |
| 有 | any | 0 | > 0 | success (稳态) | None |

**验证**: 4 个新测试(3 状态机 + 1 无 tracked assets 场景)。

**关联提交**: `fix(news): collect_news 状态机重写(全空→failure / 全 skip→success)`

## 多 Agent 修复任务划分(经验沉淀)

本次修复按"主 Agent 监督 + 4 个子 Agent 并行"组织:

| 子 Agent | 负责 bug | 文件 | 自验结果 |
|----------|---------|------|---------|
| A | #1 (CRITICAL) | `backend/collectors/base.py` | 191/191 collectors 测试通过 |
| B | #2 + #7 + #11 | `backend/services/portfolio_service.py` | 64/64 portfolio_service 测试通过 |
| C | #3 + #8 | `backend/services/evidence_builder.py` | 24/24 evidence_builder 测试通过 |
| D | #4 + #5 + #6 + #10 + #12 | 5 个文件 | 30/30 news + scheduler 测试通过 |

**主 Agent 责任**:
- 调度 4 个子 Agent 并行(子 Agent 间文件零交叉)
- 检查每个子 Agent diff 是否符合预期
- 全量 ruff + 全量 pytest 收尾验证(488/488 通过)
- 从 ISSUES.md 删除已修条目 + 写归档文件
- 一次性 git commit

**关键经验**:
- 文件零交叉时多 Agent 完全并行无冲突
- 锁测试需用 `_ObservableLock` 包装,patch import 双向(`collection_service` + `portfolio_service` 各一份)
- loguru 不桥接 stdlib `logging`,pytest `caplog` 无法捕获,需用 `logger.add(lambda ...)` 自定义 sink
- 启动期函数从 sync 改 async 时,旧测试需同步改 `async def` + `await`(否则 `RuntimeWarning: coroutine ... was never awaited`)
